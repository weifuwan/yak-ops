# Release Tooling

Release instructions for maintainers. Current checks live in the linked workflows and scripts. Reviewed version notes live in [docs/releases](../../docs/releases/README.md). Published copies and immutable release assets are recorded in [GitHub Releases](https://github.com/weifuwan/yak-ops/releases) and Git tags.

## Prepare and Verify

Prepare a release with `bash scripts/release/prepare-release-version.sh <version>` to align Maven, the frontend, Compose, `.env.example`, and `release.env`.

```sh
bash scripts/release/check-release-metadata.sh vX.Y.Z
bash scripts/release/check-release-migration.sh X.Y.Z
bash scripts/release/check-release-notes.sh X.Y.Z
```

**v1.3.0 resets Flyway to one fresh-install `V1__baseline.sql`.** Only initialize an empty MySQL database with this schema. Databases that already ran v1.0–v1.2 or any v1.3 draft migrations are **not** upgraded by this release. Take backups and recreate the database explicitly, or separately review and execute a data-preserving upgrade plan before deployment. Never point this baseline at a populated database or edit `flyway_schema_history` / run Flyway `repair` to force acceptance.

After v1.3.0 is published, V1 is immutable. Every later release with schema changes adds one new versioned SQL file, without altering previous checksums. The release migration check verifies the baseline, release sequence, and absence of implicit data rewrites in V1.

## Release Gate

Run [Release Gate](../../.github/workflows/v1-release-gate.yml) manually from `main`, with a stable `release_version` matching repository metadata. The workflow requires full Quality Check, JDBC source/sink real-database integration, versioned Playwright UI tests, distribution checks, Docker identity and Compose smoke. The formal `full` backend test selection covers the remaining registered database integration suites. Only a completed test report from the exact candidate commit can be marked PASS; skipped, missing or failed tests block the Release Gate. Required checks must actually run and succeed; UI evidence must match the candidate version and commit SHA.

Release Decision requires explicit confirmations and evidence:

- `migration_review_confirmed`, `migration_review_evidence`: audited migration or explicit no-migration justification.
- `blockers_cleared`: no unresolved P0/P1 blockers.
- `release_notes_confirmed`: the reviewed `docs/releases/vX.Y.Z.md` matches the candidate code, with Breaking Changes, Upgrade Guide and Known Limitations explicitly checked.

False confirmations and blank evidence are rejected. The Gate validates the checked-in release notes, then captures that exact Markdown plus its SHA-256, the release commit, Gate run ID and evidence references in the Actions **release-attestations artifact**. Its separately uploaded **release-candidate artifact** contains the verified distribution, SHA256SUMS and candidate evidence. Neither artifact is equivalent to a published release.

## Publish

After the Gate passes, run [Release Publish](../../.github/workflows/release-publish.yml) with `release_version`, the exact `release_commit`, the successful `gate_run_id`, and `publish_latest`. Configure `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` repository secrets before running.

Publish verifies the formal Gate run, successful Release Decision, exact commit and version, both Gate artifacts and distribution SHA-256. Docker images are built from the verified distribution, tested locally and from the registry, and published under immutable version tags. The GitHub Release body is copied from the Gate-approved Markdown without appending an autogenerated PR list, and attaches final evidence with distribution SHA-256, registry digests, release decision, Gate run and commit.

Existing Git tags and immutable image tags must match the exact release commit; mismatches block publish. `latest` is updated only after verified version images, registry smoke and GitHub Release succeed. The Gate does not publish or create a tag.

Rollback with an explicit version tag, preserve persisted state, and repair applied schema migrations forward (or restore a tested backup).
