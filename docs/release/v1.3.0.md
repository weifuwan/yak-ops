## 1. Release Goal

v1.3.0 在 v1.2.0 的 Schema-Aware Sync、Column Mapping、Auto Create Table、AUTO Runtime Planning、SMART Retry 与 Durable Recovery 基础上，重点解决三件事：

```text
一批表可以一起同步
        +
离线任务可以只同步变化的数据
        +
任务可以长期运行并主动暴露需要处理的问题
```

对应产品目标：

```text
Multi-Table
→ 一个 Task 连接一个 Source Datasource 与一个 Target Datasource
→ Task 内包含多个稳定 Table Route
→ 每张表独立 Mapping / Target / Auto Create / Execution Fact
→ 单表失败不要求重跑已经成功的全部表

Incremental
→ OFFLINE 支持 FULL / INCREMENTAL
→ 增量进度按 Table Route 独立持久化
→ 运行时冻结本次读取窗口
→ 只有成功提交后才推进 Watermark / Cursor
→ Retry / Process Restart 不丢失已确认进度

Long-Running
→ Catalog Refresh / Schema Diff
→ OFFLINE Safe Schema Evolution
→ REALTIME Continuous Reconciliation
→ Recovery Guard / Backoff / Budget
→ Derived Task Health / Attention
```

v1.3.0 不以增加更多普通用户配置项为目标。多表、增量和长期运行能力继续遵循：

> 复杂的是系统，不是用户。

运行参数、恢复策略、Schema 安全判断和底层游标事实应优先由系统持有；UI 只暴露会改变业务结果、生命周期或数据语义的必要配置。

## 2. Version Transition Boundary

本 PR 只建立 v1.3.0 Contract 与 Architecture Boundary，不修改当前 v1.2.0 Release Candidate 的产品版本、Migration、Release Evidence 或 Runtime 语义。

```text
v1.2.0
Release Candidate / Formal Release
        ↓
v1.2.0 Published
        ↓
Post v1.2 Release Transition
        ↓
1.3.0-SNAPSHOT
```

在 v1.2.0 正式发布前：

- 不把根 Maven / Frontend / Compose / release.env 版本切到 `1.3.0-SNAPSHOT`。
- 不修改已经冻结的 `V3__v1_2_0.sql`。
- 不把 v1.3 计划能力写成当前已实现能力。
- v1.3 实现 PR 必须建立在 v1.2 正式发布后的开发线之上，或在合并前完成明确 rebase / transition。

## 3. Architecture Boundary

### 3.1 Task Owns Shared Policy, Route Owns Table Semantics

v1.2 当前 Task 直接拥有一张 Source Table 与一张 Target Table。

v1.3 多表模型必须把 Task 级共同配置与表级配置拆开：

```text
DataSyncTask
├── workspace / name / syncType
├── sourceDataSourceId
├── targetDataSourceId
├── writeMode
├── runtime / retry / schedule / lifecycle
├── definitionVersion
└── tableRoutes[]
    ├── route A
    ├── route B
    └── route C
```

一个 Table Route 至少表达稳定的：

```text
route identity

source database / schema / table
        ↓
target database / schema / table

column mapping
auto create behavior
route order
```

后续增量 Cursor、Schema Baseline、Table Execution 和 Route Health 都必须能稳定关联到该 Route；不能依赖 `sourceTable + targetTable` 字符串临时拼接身份。

v1.3 多表固定边界：

```text
1 Task
1 Source Datasource
1 Target Datasource
N Table Routes
```

不支持一个 Task 同时连接多个 Source Datasource 或多个 Target Datasource。

### 3.2 Do Not Store Multi-Table Definition as One Opaque JSON Blob

Table Route 是长期产品子资源，不是一次请求里的临时数组。

原因：

- 每张表需要稳定 identity。
- 每张表需要独立增量进度。
- 每张表需要独立 Schema Baseline / Diff。
- 每张表需要独立 Execution / Retry / Metrics。
- 后续编辑单张表时不能靠替换整块 JSON 推断生命周期。

具体 DAO 表名、字段名和 Repository 由实现 PR 决定；本 Contract 只冻结“稳定子资源”这一架构要求，不在 PR0 提前锁死物理 Schema。

### 3.3 Existing Single-Table Task Must Upgrade In Place

v1.2 已存在任务不能因为 v1.3 引入 Route 而失效。

迁移语义：

```text
Existing Task
sourceTable / targetTable / mapping / autoCreateTable
        ↓
one stable Table Route
```

必须：

- 保留原 Task ID。
- 保留 Workspace。
- 保留发布状态、Schedule、Retry、Runtime 与 definitionVersion 历史语义。
- 历史 Execution / definitionSnapshot 继续可读。
- 升级不能自动重跑任务。
- 升级不能重置 REALTIME CDC state。
- 旧单表 API 消费者需要保持兼容，或通过显式兼容层归一为单 Route；不能在 Minor Version 中静默破坏已公开路径。

### 3.4 Root Execution Is Not a Table Attempt

多表以后一次 Task 运行与一张表的数据执行必须分层：

```text
Task
│
├── Table Route A
├── Table Route B
└── Table Route C

        ↓ run

Root Execution
│
├── Table Execution A
│    └── Attempt 1 / 2 / ...
├── Table Execution B
│    └── Attempt 1 / 2 / ...
└── Table Execution C
     └── Attempt 1 / 2 / ...
```

语义：

- Root Execution 表示一次 MANUAL / SCHEDULE / RECOVERY 任务运行。
- Table Execution 表示该冻结定义中的一张 Route 在本次 Root 下的执行事实。
- Attempt 继续表示一次可重试 Runtime 尝试。
- Root 汇总状态不能替代 Table Execution 的独立状态。
- 一张表失败时，其它表可以继续完成。
- Retry 默认只处理需要重试的 Table Execution，不能为了重试 1 张失败表重新执行 99 张已经成功的 APPEND 表。

具体并发调度策略不在 PR0 冻结；实现必须保持有限并发和取消传播，不建立无界线程模型。

### 3.5 Definition Snapshot Freezes All Routes

Root Execution 创建时必须冻结本次可执行定义，包括：

- Task definitionVersion。
- 本次参与的 Table Route identity 与顺序。
- Source / Target table path。
- Mapping。
- Auto Create。
- Write Mode。
- Effective Runtime Config。
- Retry Policy。
- Incremental Policy / frozen window，若适用。
- 执行所需但允许持久化的非 Secret 产品语义。

Retry、Recovery 和历史详情不得读取 Task 当前 Route 覆盖旧 Execution 的冻结定义。

Secret、password、connectionJson、token 和完整 JDBC credential 继续禁止进入 snapshot。

## 4. Multi-Table Scope

v1.3.0 的 Multi-Table 首版只进入 OFFLINE。

支持：

```text
OFFLINE
MySQL Source
   ├── users
   ├── orders
   ├── products
   └── payments
        ↓
one Target Datasource
   ├── users
   ├── orders
   ├── products
   └── payments
```

每个 Route 可以：

- 修改 Target Table 名称。
- 使用独立 Column Mapping。
- 独立开启 / 关闭 Auto Create。
- 独立完成 Schema Preview / Compatibility。
- 独立产生 Table Execution / Attempt / Metrics / Error Fact。

Task 继续统一拥有：

- Source Datasource。
- Target Datasource。
- Write Mode。
- Schedule。
- Runtime / Retry Policy。
- 上线 / 下线。
- Run / Cancel 生命周期。

v1.3 不做：

- REALTIME Multi-Table CDC。
- 一张 Source Table 写多个 Target Table。
- 多张 Source Table JOIN / MERGE 成一张 Target Table。
- 按 wildcard / prefix 自动持续纳入新表。
- 全库自动发现新表并无确认加入当前 Task。

## 5. Offline Incremental Boundary

### 5.1 Product Contract

OFFLINE 增加稳定同步方式：

```text
FULL
INCREMENTAL
```

首版增量基于单表 Route 的稳定 Cursor / Watermark，不通过用户手写任意 SQL 表达。

普通 UI 只需要表达：

```text
同步方式
全量 / 增量

增量字段
<system recommended or explicit column>
```

底层可以拥有更完整的 Cursor Contract，但不把 checkpoint serializer、window SQL、queue、batch 或 internal state 暴露给普通用户。

### 5.2 Cursor Ownership

增量状态属于 Table Route，不属于整个 Task：

```text
Task
├── users  → cursor A
├── orders → cursor B
└── payment → cursor C
```

Cursor persistence 必须满足：

- Workspace scoped。
- 可以稳定关联 Task / Route。
- 不包含数据库凭证。
- Process Restart 后仍可恢复。
- Task 其它 Route 成功 / 失败不能推进本 Route Cursor。
- 修改 Source Table、Cursor Column 或其它不兼容增量语义时不能静默复用旧 Cursor。

具体 identity 是否额外引入 routeVersion / stateVersion，由增量 Contract PR 决定；PR0 只冻结“不兼容编辑不能误复用状态”。

### 5.3 Frozen Incremental Window

每次 Table Execution 创建时冻结本次增量窗口：

```text
confirmed low watermark
        +
resolved high watermark
        ↓
frozen execution window
        ↓
read / write
        ↓
success
        ↓
advance confirmed watermark
```

失败时：

```text
confirmed watermark stays unchanged
```

Retry 必须复用同一冻结窗口，不能每次 Attempt 重新读取“当前最大值”扩大本次边界。

### 5.4 First Incremental Acceptance Boundary

v1.3 首版增量不扩展 Source Connector 矩阵，继续以当前已经真实验收的 MySQL Source 为主。

Target 继续复用现有 MySQL / PostgreSQL / Oracle JDBC Sink 能力。

增量首版不承诺：

- 任意表达式 Cursor。
- 任意自定义 WHERE。
- 多列复杂比较器的通用 DSL。
- Delete 捕获。
- Exactly-once。
- 通用 YakFlow 跨进程 Source Checkpoint。

删除捕获仍属于 CDC / Changelog 语义，不把普通 OFFLINE Incremental 包装成 CDC。

## 6. Long-Running Boundary

### 6.1 Catalog Refresh + Schema Diff

v1.3 建立可重复的 Route Schema Baseline / Refresh / Diff：

```text
accepted route schema baseline
        +
fresh datasource catalog
        ↓
Schema Diff
```

最小结构变化类型：

```text
ADD_COLUMN
DROP_COLUMN
TYPE_CHANGE
NULLABILITY_CHANGE
PRIMARY_KEY_CHANGE
```

Diff 必须基于 Logical Type / stable metadata，不通过直接比较 Source DDL 字符串实现。

v1.3 不要求建立独立、可复用、用户管理的 Logical Table Asset Catalog；为长期运行保存 Route Schema Baseline 与建设通用 Logical Table Resource 是两件事。

### 6.2 Safe Schema Evolution

v1.3 的自动目标表演进首先限定在 OFFLINE Route。

流程：

```text
Schema Diff
    ↓
Compatibility Classification
    ↓
Migration Plan
    ↓
Target Dialect DDL
    ↓
Apply
    ↓
Re-introspect Target
    ↓
Compatibility Check
```

必须：

- 安全变化才能自动 Apply。
- 删除字段、主键变化、明显收窄类型等破坏性变化默认阻断。
- DDL 执行成功后必须重新读取真实 Target Catalog。
- 不能仅根据前端 Preview 或预生成 SQL 判断完成。
- 已存在目标表的 ALTER 能力必须与 Auto Create 分开审计和测试。

具体 SAFE / RISKY / BREAKING 矩阵由 Schema Evolution PR 冻结，并必须按 MySQL / PostgreSQL / Oracle Dialect 做真实数据库验收。

REALTIME v1.3 不承诺流运行中的任意 DDL 自动传播。REALTIME 可以在启动 / 恢复边界重新校验 Schema，并在不兼容时明确阻断；在线 DDL propagation 单独进入后续版本。

### 6.3 Continuous Realtime Reconciliation

v1.2 已有：

```text
desiredState
startup reconciliation
manual restart
durable retry recovery
```

v1.3 增加单节点 Continuous Reconciliation：

```text
desiredState = RUNNING
        ↓
active execution exists?
├── yes → no action
└── no
     ↓
recovery allowed?
     ↓
controlled recovery
```

Continuous Reconciler 属于 Data Sync 产品生命周期，不属于 YakFlow Runtime。

它必须与现有 Retry / Recovery 协调：

- `RETRY_WAITING` 不能被另一个 reconciler 重复创建 Root Execution。
- 已存在 PENDING / RUNNING Execution 时不能重复启动。
- 用户主动 Stop 后必须尊重 `desiredState=STOPPED`。
- Process Startup Recovery 与 periodic reconciliation 必须共享同一 active-execution coordination。
- 恢复失败不能无限紧密循环。

### 6.4 Recovery Guard

连续恢复必须有明确 Guard：

```text
failure threshold
backoff
cooldown
recovery budget
```

超过系统允许的恢复预算后停止自动拉起并暴露 Attention Fact，等待用户处理。

v1.3 不建立分布式 ownership、leader election 或 fencing，因此 Continuous Reconciliation 仍只声明单节点正确性。

### 6.5 Task Health Is a Derived Read Model

Health 不是新的 Task Lifecycle State。

Task 原有：

```text
UNPUBLISHED / PUBLISHED
desiredState
Execution Status
```

继续保持原语义。

Health 只根据运行事实派生，例如：

- 连续失败。
- Retry Exhausted。
- Incremental Cursor 长时间未推进。
- Schema Drift。
- REALTIME desiredState=RUNNING 但缺少活动 Execution。
- Continuous Recovery Budget Exhausted。
- 最近成功时间过久。

产品可以归一为：

```text
HEALTHY
WARNING
CRITICAL
```

但 Health 不能反向篡改 Task 发布状态或 Execution 状态。

Operations Center 的目标从“展示发生过什么”进一步扩展为“告诉用户现在什么需要处理”，但不建立第二套 Runtime 状态来源。

## 7. YakFlow Boundary

v1.3 继续保持：

> Data Sync 管产品级编排与状态，YakFlow 管一条执行链的数据平面。

Multi-Table 不要求把 YakFlow 改造成产品级多任务调度器。

```text
Data Sync Root Execution
        ↓
Table Execution A → YakFlow
Table Execution B → YakFlow
Table Execution C → YakFlow
```

YakFlow 不拥有：

- Task ID / definitionVersion。
- Table Route product identity。
- Table Execution / Attempt persistence。
- Incremental confirmed watermark product state。
- Schema baseline / evolution policy。
- Recovery budget。
- Task Health。

如果底层 Source / Runtime 需要内部 checkpoint，它仍是执行机制；不能代替 Data Sync 的产品级增量 Cursor 与历史事实。

## 8. Persistence and Migration Boundary

v1.2 正式发布后：

```text
V1__baseline.sql
V2__v1_1_0.sql
V3__v1_2_0.sql
```

全部视为永久冻结历史。

v1.3 实现阶段如果需要多张 Draft Migration，可以在可重建开发 / E2E 环境使用；Release Freeze 前必须遵循 Version Management 规则 squash 为最多一个 v1.3 Release Migration。

预期：

```text
V4__v1_3_0.sql
```

如果最终没有数据库变化，则不创建空 Migration。

PR0 不创建 Migration。

## 9. Backward Compatibility

v1.3 是 Minor Release。

必须保持：

- v1.2 Task 可以读取、编辑、发布、运行。
- v1.2 单表 Task 升级后得到等价单 Route 语义。
- 历史 Execution / Attempt / Event 可读。
- 历史 definitionSnapshot 不被当前 Route Migration 重写。
- Product Version 升级不推进已有 Task definitionVersion。
- Product Version 升级不重置 REALTIME CDC state。
- 已有 OFFLINE FULL Task 不会因为新增 INCREMENTAL 默认值而自动改成增量。
- 已有 Task 不会因为新增 Safe Schema Evolution 而默认执行 ALTER，除非后续 Contract 明确给出安全兼容默认并通过迁移审查；默认优先保持旧行为。

## 9.1 Current Implementation Baseline

PR1 已开始落地 Multi-Table Persistence Foundation：

```text
DataSyncTableRoute persistence = IMPLEMENTED IN PR1
v1.2 single-table → one Route migration = IMPLEMENTED IN PR1
legacy single-table write dual-write = IMPLEMENTED IN PR1
Task detail tableRoutes read model = IMPLEMENTED IN PR1

Multi-Table Definition Snapshot = IMPLEMENTED IN PR2
Table Execution persistence / PLANNED identity = IMPLEMENTED IN PR2
Multi-Table Runtime + per-table Retry / Metrics = IMPLEMENTED IN PR3

Multi-Table Editor = NOT IMPLEMENTED
```

因此 PR1 合并后仍不能把产品描述为“已经支持多表同步”；它只建立后续 PR 可以稳定引用的 Route identity 与 persistence。

v1.3 主链按以下顺序推进：

```text

        ↓
PR2

        ↓
PR3
Multi-Table Runtime + Per-Table Retry / Metrics
        ↓
PR4
Multi-Table Sync Editor + Schema Preview
        ↓
PR5
Offline Incremental Sync Contract + Cursor State
        ↓
PR6
Offline Incremental Runtime + Durable Watermark
        ↓
PR7
Offline Incremental Editor + Cursor Visibility
        ↓
PR8
Catalog Refresh + Schema Diff
        ↓
PR9
Safe Schema Evolution + Controlled Target DDL
        ↓
PR10
Realtime Continuous Reconciliation + Recovery Guard
        ↓
PR11
Data Sync Task Health + Attention Model
        ↓
```

Release Scope Closure、Migration Squash / Freeze、Readiness、Release Candidate 与 Publish 在 Core Scope 完成后单独进入发布链，不混入能力 PR。

## 11. Automated Acceptance Boundary

v1.3 自动验收至少需要覆盖：

```text
Contract / Unit
├── legacy single-table → one route migration semantics
├── route identity / validation
├── definitionSnapshot freezes all routes
├── root / table execution state aggregation
├── per-table retry isolation
├── incremental cursor / frozen window / success-only advance
├── schema diff classification
├── schema evolution safety matrix
├── continuous reconciliation coordination
├── recovery guard / budget
└── health derivation

Real Database Acceptance
├── OFFLINE Multi-Table
│   └── MySQL Source → MySQL / PostgreSQL / Oracle
│       + Mapping / Auto Create / partial failure
├── OFFLINE Incremental
│   └── MySQL Source → MySQL / PostgreSQL / Oracle
│       + retry / process restart / cursor persistence
├── OFFLINE Schema Evolution
│   └── safe apply + destructive change block
└── REALTIME Reconciliation
    └── MySQL CDC existing single-table matrix
        + desired-state recovery / no duplicate active root
```

正式 Release Gate 继续要求 Full Backend Acceptance，不允许因 path filter 跳过本版本要求的真实数据库场景。

## 12. Required Manual E2E Baseline

PR0 先冻结最小产品场景，执行步骤与最终编号由后续 E2E PR 落文档。

至少包含：

```text
MULTI-001
OFFLINE MySQL → PostgreSQL
5 routes
Mapping + Auto Create
→ all success

MULTI-002
5 routes
1 route fails
→ other routes continue
→ retry only failed route

INCREMENTAL-001
initial full / incremental baseline
→ add new source rows
→ next run only reads expected incremental window
→ restart Yak Ops
→ confirmed cursor preserved

SCHEMA-001
source adds safe nullable column
→ diff detected
→ target evolves
→ subsequent sync succeeds

SCHEMA-002
destructive / incompatible schema change
→ no automatic destructive ALTER
→ route exposes actionable failure / attention

RECOVERY-001
REALTIME desiredState=RUNNING
→ active execution disappears / fails outside retry chain
→ continuous reconciliation performs guarded recovery
→ no duplicate active root
```

人工 E2E 验证用户可见产品路径；数据库 × 写入模式 × 参数的矩阵继续由自动 Acceptance 承担。

## 13. Frozen Non-Goals

以下能力明确不进入 v1.3.0 Core Scope：

- REALTIME Multi-Table CDC。
- Multi-Source / Multi-Target Task。
- Full Database wildcard sync / 自动持续发现并纳入新表。
- Transform / Expression / Custom SQL Mapping。
- JOIN / Aggregate / Computed Column。
- PostgreSQL CDC 或更多 CDC Source。
- 在线 REALTIME 任意 DDL 自动传播。
- 独立可复用的 Logical Table Asset Catalog 产品面。
- 用户可配置的底层 Runtime Tuning UI。
- 用户可配置复杂 Retry / Recovery 内部参数。
- Distributed Runtime / Worker / HA / leader election / fencing。
- Exactly-once transaction coordination。
- 通用 YakFlow checkpoint 跨进程恢复承诺。
- Runtime Trace 对象存储、全文检索或大规模日志平台化。

## 14. PR0 Completion Criteria

本 PR 完成时只要求：

- v1.3.0 Product Theme 明确为 Multi-Table + Incremental + Long-Running。
- Multi-Table Task / Table Route / Table Execution 三层职责冻结。
- OFFLINE Incremental Cursor ownership 与成功后推进原则冻结。
- Schema Diff / Safe Evolution / REALTIME Continuous Reconciliation 边界冻结。
- Task Health 明确为 Derived Read Model。
- v1.3 与 YakFlow、Datasource、Boot 的 ownership 不发生倒置。
- Non-Goals 明确。
- Delivery Sequence 明确。
- 不修改当前 Runtime。
- 不创建 v1.3 Migration。
- 不切换当前 Repository Product Version。
